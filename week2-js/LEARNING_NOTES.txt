Week 2 (JS) - Learning Notes
=============================

Three exercises on LangChain.js fundamentals: reusable prompt templates, the
different ways to invoke a chat model, and an end-to-end structured-output
pipeline built with LCEL Runnables/Chains. All three go through OpenRouter
with a single API key, using a free-tier GPT-OSS model (see config.ts).

1. ChatPromptTemplate is a template object, not a string
----------------------------------------------------------
`ChatPromptTemplate.fromMessages([...])` (prompts.ts) is built once and
formatted many times via `.formatMessages({...})`, which returns the actual
`BaseMessage[]` array `chat.invoke()` expects. The payoff shows up in
promptTemplateDemo.ts: the same `explainerPromptTemplate` is formatted with
three different `{topic}/{audience}` pairs without ever touching a prompt
string by hand. `.partial({...})` goes one step further - it returns a *new*
template with some variables pre-filled (`reviewRewritePromptTemplateBase`
fixes `{style}`, leaving only `{review}` to supply later), which is the
LangChain equivalent of currying a function over one of its arguments.

2. LangChain.js has no invoke()/ainvoke() split - only invoke()/stream()
------------------------------------------------------------------------------
Python LangChain has four real, distinct methods: invoke() (blocking),
ainvoke() (awaited coroutine), stream() (blocking generator), astream()
(async generator). LangChain.js only has two: `.invoke()` and `.stream()`,
and both already return a Promise / Promise<AsyncIterable> - there's no
"blocking" version to accidentally call synchronously, because JS has no
such thing as a blocking network call in the first place. invocationMethodsDemo.ts
handles this by demonstrating the *behavior* Python's ainvoke()/astream() are
for - concurrent, non-blocking calls - as the same invoke()/stream() calls
fired via `Promise.all` instead of awaited one at a time in a loop. The
comparison that matters isn't "which method did I call" (JS only offers one
per behavior), it's "did I await each call before starting the next, or let
them all run concurrently."

3. Why concurrent invoke() is faster, mechanically
--------------------------------------------------------
Each `chat.invoke(prompt)` call is I/O-bound: almost all of its wall-clock
time is spent waiting on OpenRouter's network response, not doing local CPU
work. Sequential invoke() calls wait for that response before starting the
next request, so total time is roughly the sum of every individual latency.
Concurrent invoke() calls (via `Promise.all`, capped by the hand-written
`Semaphore` class in invocationMethodsDemo.ts, the JS analog of Python's
`asyncio.Semaphore`) start the next request the instant the previous one
hands off to the network, so total time approaches the *slowest single
request* rather than the *sum of all of them*. This is the same reasoning
week2's original sync-vs-async benchmark demonstrated, now folded into the
invocation-methods exercise instead of being a separate one.

4. LCEL / Runnables: `.pipe()` and `RunnableSequence.from([...])`
------------------------------------------------------------------------
reviewAnalysisPipeline.ts builds two chains, both shaped
`prompt -> model -> (something that produces structured output)`:
  RunnableSequence.from([reviewAnalysisPromptTemplate, structuredChat])
  RunnableSequence.from([reviewAnalysisWithFormatInstructionsPromptTemplate, chat, parser])
Every step in the sequence is a `Runnable` - something with a uniform
`.invoke(input)` interface - so `RunnableSequence` just feeds each step's
output as the next step's input, ending with whatever the last step
returns. This is the same idea as Python's LCEL `prompt | model | parser`
syntax; LangChain.js just spells composition as `RunnableSequence.from([...])`
(or `.pipe()` chained off any single Runnable) instead of overloading `|`.

5. Two ways to get structured output, and the actual tradeoff
------------------------------------------------------------------
Implementation A - `model.withStructuredOutput(schema)`: LangChain generates
the format instructions and handles parsing/validation for you, usually via
tool-calling under the hood. Less code, less visibility into what's actually
being sent to the model or how the raw reply gets turned into JSON.
Implementation B - `StructuredOutputParser.fromZodSchema(schema)`: you inject
`parser.getFormatInstructions()` into the prompt yourself
(reviewAnalysisWithFormatInstructionsPromptTemplate), the model replies with
text, and the parser step turns that text into validated JSON. More code,
but every step (what instructions were given, what came back, how it was
validated) is visible and swappable. Both are run over the same 10 reviews
in reviewAnalysisPipeline.ts specifically so their success rate and timing
can be compared side by side rather than assumed equivalent.

6. zod schema -> TypeScript type in one definition
----------------------------------------------------------
`ReviewAnalysisSchema` (schemas.ts) is a runtime validator (`.parse()`
throws a ZodError on a shape mismatch) *and*, via `z.infer<typeof
ReviewAnalysisSchema>`, a compile-time TypeScript type (`ReviewAnalysis`).
One definition gives two guarantees - the pipeline's return type is checked
against the exact same schema used to validate the model's actual JSON reply
at runtime - instead of maintaining a hand-written interface that could
silently drift from the validation logic.

7. Retry logic is still transport-level, not schema-level, here
------------------------------------------------------------------------
`models.ts`'s `ainvokeWithRetry` (exponential backoff on network errors /
429s / 5xxs) is used by reviewAnalysisPipeline.ts so one flaky free-model
response doesn't fail the whole 10-review batch. This is deliberately
separate from schema validation: `withStructuredOutput()` and
`StructuredOutputParser` both throw if the model's reply doesn't match
`ReviewAnalysisSchema`, and `runPipeline()` in reviewAnalysisPipeline.ts
catches that per-review and records it as a failed row instead of retrying
it - the assignment asks to *compare* the two implementations' success
rates, so a schema failure is a data point, not something to paper over with
a retry loop the way week2's earlier extraction exercise did.

8. Running it
------------------
Set OPENROUTER_API_KEY in `.env` first (see README.md). None of the numbers
above are specific measured results - run `npm run invocation-demo` and
`npm run review-pipeline` yourself to see actual timings and success rates
for your account/network; they'll vary by model load and free-tier rate
limits.
