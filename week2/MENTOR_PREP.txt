SECTION 1 - PROJECT ARCHITECTURE
================================================================================

Q1: Why FastAPI this week instead of a CLI menu like week1?

A: Because week2's actual topic is building robust BACKEND INTEGRATIONS, not
   one-off scripts - the assignment explicitly frames it that way. A CLI menu
   can't demonstrate an HTTP streaming endpoint, a client disconnecting
   mid-request, or a POST endpoint returning proper HTTP status codes on
   validation failure. FastAPI is the natural fit because these exercises are
   literally "build an endpoint that..." - the deliverable IS a service.

Q2: Why keep LangChain instead of the raw openai SDK, given this week is
    about lower-level API mechanics (streaming, JSON schema, tool calls)?

A: Consistency with week1's model-abstraction lesson - model_name is still
   just a string, and switching STREAM_MODEL/EXTRACTION_MODEL/BENCHMARK_MODEL
   in config.py doesn't touch any logic file. LangChain's ChatOpenAI still
   exposes the raw mechanics needed here: .astream() for token-by-token
   streaming, model_kwargs for passing response_format straight through to
   the request body, and .bind_tools() for real function calling - none of
   that is hidden by the abstraction, it's just wrapped consistently.

Q3: Why two separate retry mechanisms (models.ainvoke_with_retry vs.
    extraction.py's loop) instead of one?

A: They fire on different failures and want different responses. tenacity's
   exponential-backoff retry (models.py) fires when the REQUEST itself failed
   - dropped connection, 429, 5xx - and backing off gives the provider time
   to recover. The plain for-loop in extraction.py fires when the request
   SUCCEEDED but the model's ANSWER failed schema validation - there's no
   reason to wait longer before trying again, since the problem was the
   model's output, not network conditions. Merging them would mean either
   needlessly delaying validation retries or retrying network failures with
   no backoff at all.

Q4: What happens if the extraction endpoint's model consistently returns bad
    JSON? Walk me through exactly what the caller sees.

A: extraction.extract_support_ticket() tries up to EXTRACTION_MAX_RETRIES (3)
   times, logging each rejected attempt's error. If all 3 fail, it returns
   {"ticket": None, "attempts": 3, "error": "could not extract a valid ticket
   after 3 attempts. Last error: ..."}. app.py's /extract endpoint sees
   result["error"] is set and raises HTTPException(422, detail=...) - the
   caller gets a proper HTTP 422 with the actual last validation error as the
   detail message, not a 200 with null/garbage data, and not an unhandled
   500 either.

Q5: What did you actually measure, not just claim, for Exercise 3?

A: 6 short prompts, nvidia/nemotron-3-nano-30b-a3b:free, concurrency 3:
   sync totaled 25.47s (avg latency 4.12s, throughput 0.236 req/s), async
   totaled 7.07s (avg latency 2.49s, throughput 0.848 req/s) - a measured
   3.60x wall-clock speedup, with peak memory essentially unchanged (119.4MB
   vs 120.6MB). That's one real run's numbers, printed in README.md and
   LEARNING_NOTES.txt exactly as produced, not a theoretical estimate.


================================================================================
SECTION 2 - EXERCISE 1 / SSE STREAMING
================================================================================

Q6: Explain SSE in one sentence, then explain why it's not "just WebSockets."

A: SSE is a single ordinary HTTP response the server keeps open and writes
   to incrementally, formatted as `data: ...` lines separated by blank
   lines - not a separate protocol or connection type. It's one-directional
   (server to client only) and rides on plain HTTP, so it works through
   normal proxies/load balancers/auth without a protocol upgrade handshake;
   WebSockets are full-duplex and require that upgrade - more capability
   than a "stream this answer" endpoint needs.

Q7: Why GET instead of POST for /ask/stream?

A: Browsers' native EventSource client - the standard way to consume SSE
   from a browser - can only issue GET requests. This project's endpoint
   takes `question` as a query parameter for that reason. A backend-only
   client like stream_client.py doesn't strictly need GET (it's not using
   EventSource), but keeping the endpoint GET means it also works with a
   real browser client with zero changes.

Q8: How exactly do you detect a client disconnect, and why check it on every
    chunk instead of once at the start?

A: `await request.is_disconnected()`, a FastAPI/Starlette built-in, checked
   inside the async for loop before yielding each SSE event. A single check
   before the loop starts would only catch a client that's already gone
   before the first token; real disconnects happen mid-stream (user closes
   the tab three sentences in). Checking every iteration means the loop
   notices within about one token and stops pulling further chunks from
   chat.astream() - which matters because every chunk not yet generated is
   OpenRouter quota (and, in a paid system, money) not yet spent.

Q9: What actually gets logged, and why does that matter? (GOTCHA - they may
    ask you to produce a real log line from memory)

A: Every request gets a short request_id, logged at start (question text)
   and at completion. A clean finish logs elapsed seconds, chunk count, and
   character count; a disconnect logs elapsed time and chunks sent before
   the client left; an error logs elapsed time and the exception. Real
   example from this project's own test run:
     "[45025e6c] request latency: 6.68s - 44 chunks, 245 chars, ~73 tokens
     (estimated)"
   This matters because in production you can't watch every stream live -
   these log lines are how you'd answer "why was this request slow" or
   "how many users are abandoning mid-stream" after the fact.

Q10: If yielding an SSE event after the client disconnected doesn't raise an
     exception, how do you know your disconnect handling is actually doing
     anything? (GOTCHA)

A: Fair pushback - is_disconnected() existing doesn't prove it's wired up
   correctly. The proof is behavioral: the loop `break`s as soon as
   is_disconnected() returns True, so no further `chat.astream()` iteration
   happens and no further event is yielded - verified by the log line
   itself, which only appears in the disconnected branch ("client
   disconnected after N chunks / Ts - stopped generating") and reports a
   chunk count lower than what a full response would have produced. If the
   check weren't wired up, that log line would never appear and the full
   response would always complete regardless of the client leaving.

SECTION 3 - EXERCISE 2 / STRUCTURED EXTRACTION
================================================================================

Q11: Why EmailStr and Literal enums in the schema instead of plain `str` for
     every field? (KEY QUESTION)

A: Because plain `str` accepts anything, which means nothing is actually
   being validated - the schema would only check "did I get 5 keys," not
   "is this data correct." EmailStr rejects a malformed email address;
   Literal["low","medium","high","urgent"] rejects any priority value
   outside that exact set (e.g. the model writing "asap" instead of
   "urgent"). Those are exactly the kinds of subtly-wrong-but-JSON-shaped
   answers "reject malformed responses" is asking you to catch - a plain
   str schema would silently accept them.

Q12: Why response_format json_object AND PydanticOutputParser? Isn't one
     enough?

A: They catch different failure classes. JSON mode is a SYNTAX guarantee
   from the backend - "the reply will parse as JSON" - but says nothing
   about which keys or types are inside it; {"foo": "bar"} still satisfies
   json mode. PydanticOutputParser is what actually checks the JSON matches
   SupportTicket's fields, types, and enums. Json mode alone would still let
   a validly-JSON-but-wrong-shaped reply through; Pydantic alone (without
   json mode) means fighting a model that might still wrap its answer in
   prose or ```json fences, making even the parse step unreliable. Together,
   json mode narrows failures down to "wrong data," and Pydantic is what
   catches wrong data.

Q13: Why not just use LangChain's with_structured_output() here - isn't that
     the recommended way?

A: It usually is, and it's simpler when it works. Two reasons it's not used
   here: (1) with_structured_output's default path relies on native function
   calling, which not every free OpenRouter model reliably supports -
   tool_calling_demo.py's own fallback branch exists because of exactly this
   uncertainty; (2) the assignment explicitly asks you to implement reject
   and retry logic yourself, which with_structured_output would mostly hide
   inside the library. Building it with an explicit PydanticOutputParser and
   a visible retry loop makes both the validation and the retry behavior
   something I can point to and explain, not something happening inside a
   framework method.

Q14: Walk through what happens on attempt 2, if attempt 1 fails.

A: Attempt 1 calls the model (via models.ainvoke_with_retry, which itself
   may internally retry 3x on pure network failures), gets a response, and
   tries parser.parse() on it. If that raises OutputParserException or
   ValidationError, extraction.py logs a warning with the first 200 chars of
   the error and the for-loop moves to attempt 2 - a COMPLETELY FRESH call
   to the model (new sampling, same prompt), not a retry of the exact same
   failed text. If attempt 2 also fails, attempt 3 runs the same way; if
   that fails too, the function returns the error dict and app.py turns it
   into a 422.

Q15: All 3 sample emails succeeded on attempt 1 in your test run - so did you
     actually prove the retry logic works? (GOTCHA)

A: Not from that run alone, no - a clean run is expected most of the time
   with a capable free model and a well-specified schema; it's evidence the
   HAPPY PATH works, not that the retry path does. The retry path's logic is
   still verifiable by reading extraction.py directly: the except clauses
   specifically catch OutputParserException and ValidationError (not a bare
   except-and-continue), the loop bound is config.EXTRACTION_MAX_RETRIES, and
   the failure return shape is exercised by app.py's 422 branch regardless of
   how it's triggered. To actually force it, you'd feed in a request that
   makes json mode syntactically valid but semantically wrong - e.g. a very
   ambiguous or content-free email where the model has to guess a priority -
   or temporarily lower EXTRACTION_MAX_RETRIES and picture a model that keeps
   picking an out-of-enum priority value. I called this out rather than
   claim the retry path was proven by a run where it never actually fired.

SECTION 4 - EXERCISE 3 / SYNC VS ASYNC
================================================================================

Q16: Why did async win here - what's actually different at the OS/interpreter
     level? (KEY QUESTION)

A: Each LLM call is I/O-bound - nearly all its wall time is spent waiting on
   a network response, with negligible actual CPU work in our process. In
   sync code, chat.invoke() blocks the whole thread for that entire wait;
   nothing else can happen. In async code, awaiting chat.ainvoke() suspends
   just that one coroutine and returns control to the event loop, which
   starts another coroutine's request during the first one's wait - and
   because the GIL is released while waiting on network I/O, those waits
   genuinely overlap rather than one blocking the others. Total time
   approaches (total work) / (concurrency) instead of the sum of every
   individual wait.

Q17: Would this same async approach speed up CPU-heavy work (like local text
     processing) as much as it did here? (GOTCHA)

A: No - and that's the tell for whether async is the right tool. Async
   concurrency helps when a task is WAITING, not when it's computing; the
   GIL means only one thread runs Python bytecode at a time regardless of
   async/await, so CPU-bound work doesn't get faster from asyncio.gather()
   the way I/O-bound network waits do. Heavy local computation would need
   multiprocessing (real parallel processes) or moving the work off-process
   entirely, not asyncio.

Q18: Why cap concurrency at 3 instead of firing all 6 requests at once?

A: Two reasons: it's the async equivalent of week1's REQUEST_DELAY_SECONDS -
   a simple way to stay under OpenRouter's free-tier 20 requests/minute cap
   - and it demonstrates the realistic pattern. Firing every request
   unbounded works fine at 6 prompts but doesn't scale; with more prompts
   (or more concurrent users hitting a real endpoint), unbounded concurrency
   risks a burst of 429s. asyncio.Semaphore(config.ASYNC_CONCURRENCY) caps
   how many coroutines are actually mid-request at once, regardless of how
   many are queued.

Q19: Peak memory was almost identical between sync and async (119.4MB vs
     120.6MB) - doesn't concurrency use more memory? Why didn't it show up?

A: At this scale, no - both modes hold a small, bounded number of
   request/response objects in memory at any instant: one at a time in
   sync, at most ASYNC_CONCURRENCY (3) at a time in async. That's a tiny
   difference in absolute terms, easily lost in the noise of everything
   else already loaded in the process (LangChain, the interpreter itself).
   Memory isn't the axis this technique optimizes for - concurrency trades
   a small, bounded amount of memory for a large amount of overlapped wait
   time. At a much larger scale (thousands of concurrent requests) you
   would expect memory to grow with concurrency; it just isn't the
   bottleneck at 3-way concurrency over 6 prompts.

SECTION 5 - FUNCTION / TOOL CALLING (BONUS)
================================================================================

Q20: The model "requested" a tool call - does that mean it ran the function?

A: No, and this is the most commonly misunderstood part of tool calling.
   The model only ever emits a structured REQUEST - "call this tool with
   these arguments" - as part of its response. It has no ability to execute
   code. Our own code (tool_calling_demo.py) is what actually calls
   lookup_priority_policy.invoke(tool_call["args"]) and gets a real return
   value; the model doesn't see that value until we explicitly send it back
   in a new ToolMessage on the next request.

Q21: What would happen if the model doesn't support tool calling on
     OpenRouter?

A: ai_message.tool_calls would just be an empty list, and
   tool_calling_demo.py's if-branch handles that explicitly: it prints the
   model's direct answer and a note explaining tool calling likely isn't
   supported for that model, then exits cleanly - no crash, no silent wrong
   behavior. This mirrors the same "honest about free-tier variability"
   stance week1 took about which free models happen to be available.

SECTION 6 - THE 5 GOTCHA ANSWERS TO REMEMBER
================================================================================

1. "Doesn't yielding an SSE event after disconnect prove nothing, since it
   won't raise?" -> Correct concern; the proof is behavioral - the loop
   breaks and stops calling astream() the moment is_disconnected() is True,
   verified by a lower chunk count in the disconnect log line versus a
   completed response.

2. "All 3 sample extractions succeeded first try - did you prove the retry
   path?" -> No, that proves the happy path. The retry path is verified by
   reading the code (specific except clauses, bounded loop, tested failure
   return shape via the 422 branch), not by a run where it never triggered.

3. "Would async help CPU-bound work the same way?" -> No - the GIL means
   only I/O waits actually overlap; CPU-bound work needs multiprocessing,
   not asyncio.

4. "JSON mode already gives me valid JSON, why also validate with
   Pydantic?" -> JSON mode guarantees syntax, not shape - a syntactically
   valid but wrong-shaped or out-of-enum reply passes json mode and fails
   Pydantic. You need both.

5. "Peak memory barely changed between sync and async - so what did async
   actually save?" -> Wall-clock time, specifically the overlap of network
   WAIT time, not CPU or memory. That's the axis this technique optimizes.


================================================================================
SECTION 7 - TWO THINGS TO PRACTICE FROM MEMORY
================================================================================

A) THE SSE WIRE FORMAT:
   event: <name>          (optional)
   data: <payload>
   <blank line>            <- required; this is what completes the event
   It's plain HTTP with Content-Type: text/event-stream, kept open and
   written to incrementally. No separate protocol, no upgrade handshake.

B) THE TWO RETRY LAYERS:
   - Transport retry (tenacity, exponential backoff): request itself
     failed (network/429/5xx) - same request, wait and try again.
   - Schema retry (plain loop, no backoff): request succeeded, answer
     failed validation - fresh call, no reason to wait.
